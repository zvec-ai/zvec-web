An advanced graph-based index that combines the [HNSW](../hnsw-index/) graph structure with [RaBitQ](https://arxiv.org/abs/2405.12497) quantization algorithm — delivering **dramatically lower memory usage** while maintaining state-of-the-art search quality.

<Callout className="text-base" type="warn">
  **Platform Requirement**: HNSW-RaBitQ is currently supported **only on x86_64** with **AVX2** or higher instruction set support. It is not available on ARM architectures.
</Callout>

## How It Works

HNSW-RaBitQ combines two techniques to achieve high recall with minimal memory:

- **HNSW graph for navigation** 🪜
  - Same multi-layer graph structure as the standard [HNSW index](../hnsw-index/) — sparse upper layers for fast long-range jumps, dense lower layers for fine-grained local search.
- **RaBitQ for distance estimation** 🗜️
  1. During **training**, the algorithm clusters vectors via KMeans and learns a random rotation matrix. Each vector is then quantized into a compact binary representation (as few as configurable 1–9 bits per dimension).
  1. During **search**, the query vector is transformed using the same rotation, and distances to candidate nodes are *estimated* using fast binary inner-product operations on the quantized data — instead of full FP32 distance computations.
  1. The key insight: **graph construction uses original FP32 vectors** for maximum accuracy, while **search uses quantized vectors** for speed and low memory. This separation ensures graph quality is never compromised by quantization.

### Why This Matters

In a standard HNSW index, every search step requires loading full FP32 vectors to compute exact distances. For 768-dimensional vectors, that's 3 KB per node — and a single query may visit thousands of nodes.

With RaBitQ quantization at 7 bits per dimension, each vector shrinks to roughly **672 bytes** — a **~4.6x reduction**. At the extreme end, 1-bit quantization compresses each vector to just **96 bytes** — a **~32x reduction**. Since the HNSW graph traversal is memory-bound, smaller vectors translate directly to faster search and lower memory footprint.

## When to Use HNSW-RaBitQ?

- ✅ Large-scale datasets where memory is a constraint (billion scale of vectors)
- ✅ High-dimensional embeddings (1536–4095 dimensions) where FP32 storage is expensive
- ✅ Production systems requiring low-latency search with controlled memory budgets
- ✅ Workloads on **x86_64** servers with AVX2/AVX-512 support

<Callout className="text-base" type="idea">
  **Best Practice**: Use HNSW-RaBitQ when you need the search quality of HNSW but cannot afford its full memory footprint. The `total_bits` parameter (1–9) lets you fine-tune the accuracy–memory trade-off: **7 bits** achieves ~99% recall, **5 bits** ~95%, and **4 bits** ~90% — all without raw vector reranking. Going as low as **1 bit** maximizes compression at the cost of lower recall.
</Callout>

## Advantages

1. ✨ **Significantly lower memory footprint** — Quantized vectors can be up to 32x smaller than FP32, reducing active index memory
1. ✨ **Faster search** — Binary distance estimation is considerably cheaper than FP32 computation, especially with AVX2/AVX-512 acceleration
1. ✨ **Near-HNSW recall** — Graph construction uses original vectors, so graph quality matches standard HNSW. RaBitQ's 7-bit mode achieves ~99% recall according to [the paper](https://arxiv.org/pdf/2409.09913)
1. ✨ **Tunable compression** — `total_bits` lets you choose your accuracy–memory trade-off

## Trade-offs

1. ⚠️ **x86_64 only** — Requires AVX2 or higher instruction set; not available on ARM
1. ⚠️ **Training overhead** — Requires a KMeans training step before index construction, adding to build time
1. ⚠️ **Dimension constraints** — Vector dimensions must be between 64 and 4095

## Key Parameters

<Callout className="text-base" type="idea">
  **Tuning Tip**:
  Start with the defaults (`total_bits=7`, `num_clusters=16`). Adjust `ef` first for recall/latency trade-offs at query time. Only reduce `total_bits` if you need to cut memory further and can tolerate slightly lower recall.
</Callout>

### Index-Time Parameters

<div className="flex flex-row flex-wrap gap-3 items-center">
  <PythonLinkButton url="/api-reference/python/params/#zvec.model.param.HnswRabitqIndexParam" label="Python API Reference" />
</div>

| Parameter | Description | Tuning Guidance |
| --------- | ----------- | --------------- |
| `metric_type` | **Similarity metric** used to compare vectors (`L2`, `IP`, or `COSINE`) <br /> Defaults to `IP` | Choose based on how your embeddings were trained |
| `m` | **Max neighbors per node** — The maximum number of bidirectional links per node in the HNSW graph <br /> Defaults to `50` | • Higher `m` → <br /> ✨ better recall and graph connectivity <br /> ⚠️ more memory and slower build |
| `ef_construction` | **Index-time candidate pool size** — How many candidates the algorithm explores when inserting each vector <br /> Defaults to `500` | • Higher `ef_construction` → <br /> ✨ better graph quality <br /> ⚠️ longer build time (*does not affect query speed*) |
| `total_bits` | **RaBitQ quantization bits per dimension** — Controls the precision of the binary encoding. Valid range: **1–9** <br /> Defaults to `7` | • `7` bits → ~99% recall <br /> • `5` bits → ~95% recall <br /> • `4` bits → ~90% recall <br /> • `1` bit → maximum compression, lowest recall <br /> ⚠️ Lower values save more memory but reduce accuracy |
| `num_clusters` | **Number of KMeans clusters** — Used during the RaBitQ training phase to partition the vector space <br /> Defaults to `16` | • More clusters can capture finer distribution patterns <br /> • Higher values increase recall slightly |
| `sample_count` | **Training sample count** — Number of vectors sampled for KMeans training (`0` = use all vectors) <br /> Defaults to `0` | • Set a smaller value(e.g. 5,000,000) to speed up training and reduce memory usage on very large datasets |

### Query-Time Parameters

<div className="flex flex-row flex-wrap gap-3 items-center">
  <PythonLinkButton url="/api-reference/python/params/#zvec.model.param.HnswRabitqQueryParam" label="Python API Reference" />
</div>

| Parameter | Description | Tuning Guidance |
| --------- | ----------- | --------------- |
| `ef` | **Query-time candidate pool size** — How many candidates are explored during graph traversal at search time | • Higher `ef` → <br /> ✨ higher recall <br /> ⚠️ higher query latency |
| `radius` | **Distance (similarity) threshold** for range-based filtering — only documents satisfying the threshold are returned | Example: <br /> • With inner product `MetricType.IP`, set `radius=0.6` to keep only results with score > 0.6 <br /> ✅ Use when: Filtering out low-quality matches <br /> 🚫 Skip when: You want all top-k results |
| `is_linear` | Forces a **brute-force linear search** instead of using the HNSW graph | 🐌 Very slow for large datasets! <br /> ✅ Only use for: Debugging or verifying index accuracy |
| `is_using_refiner` | **Enables exact score refinement** — recomputes exact FP32 distances for top candidates after quantized search | ✅ Turn on: When you need maximum precision <br /> ⚠️ Adds latency due to full-precision re-scoring |

## Usage

### Creating a Collection with HNSW-RaBitQ

```python title="Create a collection with HNSW-RaBitQ index"
import zvec

collection = zvec.create_and_open(
    path="/path/to/my/collection",
    schema=zvec.CollectionSchema(
        name="my_collection",
        fields=[
            zvec.FieldSchema(
                name="title",
                data_type=zvec.DataType.STRING,
            ),
        ],
        vectors=[
            zvec.VectorSchema(
                name="embedding",
                data_type=zvec.DataType.VECTOR_FP32,
                dimension=768,
                # [!code word:HnswRabitqIndexParam]
                index_param=zvec.HnswRabitqIndexParam(  # [!code highlight]
                    metric_type=zvec.MetricType.COSINE,
                    m=16,
                    ef_construction=200,
                    total_bits=7,
                    num_clusters=64,
                ),
            ),
        ],
    ),
)
```

### Inserting Documents

```python title="Insert documents"
docs = [
    zvec.Doc(
        id=f"doc_{i}",
        fields={"title": f"Document {i}"},
        vectors={"embedding": [0.1 * i + 0.01 * j for j in range(768)]},
    )
    for i in range(1000)
]
collection.insert(docs)
```

### Querying

```python title="Search with HNSW-RaBitQ"
# [!code word:HnswRabitqQueryParam]
results = collection.query(
    zvec.VectorQuery(
        field_name="embedding",
        vector=[0.1] * 768,  # Replace with your actual query vector
        param=zvec.HnswRabitqQueryParam(ef=300),  # [!code highlight]
    ),
    topk=10,
)
```

### Querying with Filters

```python title="Filtered search"
results = collection.query(
    zvec.VectorQuery(
        field_name="embedding",
        vector=[0.1] * 768,
        param=zvec.HnswRabitqQueryParam(ef=300),
    ),
    topk=10,
    filter="title = 'Document 42'",  # [!code highlight]
)
```

### Querying with Refiner

When you need the highest possible accuracy, enable the refiner to recompute exact distances for the top candidates:

```python title="Search with exact score refinement"
results = collection.query(
    zvec.VectorQuery(
        field_name="embedding",
        vector=[0.1] * 768,
        param=zvec.HnswRabitqQueryParam(
            ef=300,
            is_using_refiner=True,  # [!code highlight]
        ),
    ),
    topk=10,
)
```

### Optimizing the Collection

After bulk inserts, optimize to rebuild segments and improve search performance:

```python title="Optimize the collection"
collection.optimize()
```

## HNSW vs HNSW-RaBitQ

| Aspect | [HNSW](../hnsw-index/) | HNSW-RaBitQ |
| ------ | ---- | ----------- |
| **Quantization method** | Standard [quantization](../quantization/) via `quantize_type` — supports **INT8**, **FP16**, **INT4** | Built-in **RaBitQ** binary quantization (1–9 bits per dimension) |
| **Memory per vector** (768-dim) | ~3 KB (FP32), ~1.5 KB (FP16), ~768 B (INT8), ~384 B (INT4) | ~864 B (9-bit) to ~96 B (1-bit) |
| **Search distance computation** | Exact FP32 (or quantized integer/fp16 arithmetic when quantized) | Fast binary inner-product estimation via RaBitQ |
| **Recall** (typical) | ~99%+ (FP32), slightly lower when quantized | ~90–99% (tunable via `total_bits`) |
| **Graph construction quality** | FP32 | FP32 (same quality) |
| **Refiner support** | ✅ Recomputes exact FP32 distances for quantized results | ✅ Same — recomputes exact FP32 distances |
| **Platform** | All supported platforms | x86_64 only (AVX2 or higher required) |
| **Best for** | General-purpose production; use with INT8/FP16 for moderate memory savings | Maximum compression with RaBitQ-specific optimizations on x86_64 |

<Callout className="text-base" type="idea">
  **How to choose**: If you need cross-platform compatibility, use the standard [HNSW index](../hnsw-index/) with [`quantize_type`](../quantization/) set to `INT8` or `FP16` — this already provides significant memory savings. Choose HNSW-RaBitQ when you are on x86_64 and want RaBitQ's specialized binary quantization, which can offer better accuracy-compression trade-offs at comparable memory levels.
</Callout>
